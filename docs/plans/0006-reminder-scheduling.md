# Plan 0006: Reminder scheduling (A4)

Status (2026-11-20): implemented for Android and verified on two devices (Pixel 8 on 2026-11-13, Pixel 5 on 2026-11-17); slices N1 to N7 are done (see "Blockers and next action"). Open: iOS is untested (the soft bell file is not yet in the Xcode project, so iOS plays the default sound); T20 (transition look) and the onboarding notify screen on a small screen were not tested; Android TV is unverified; the second independent review (after N5) is not recorded; the docs named in N5 are updated by the 2026-11-20 refresh (`PRODUCT_BRIEF.md`, `GLOSSARY.md`, `platform-notes.md`). History: the plan was drafted on 2026-11-12 for Fox's review. Requirements owner: Fox. Tracker: pending. Criterion IDs: `RS-n`.

## Outcome

An anniversary with its reminder on produces a local notification on the right day and time, without opening the app: at the stored time, `remindDaysBefore` days before the next occurrence, repeating every year. The three system events (mùng 1, rằm, Tết festivals) do the same when their Settings switches are on. Editing, deleting, toggling, changing a setting, granting the permission or rebooting never leaves a stale or missing notification.

## Scope

In:
- A pure planner that turns anniversaries, settings, "now" and the lunar engine into a list of planned reminders inside a window.
- A `NotificationGateway` port with one `flutter_local_notifications` adapter (schedule, cancel all, list pending, tap payload).
- One idempotent `syncReminders()` that makes the OS pending set equal the plan. Triggers: app start, any change to anniversaries (repository stream), any change to the reminder-related settings, notification permission change, app resume (a day has passed).
- Per-event reminders (D9) and system-event reminders (Settings switches, plan 0005 D14), notification text in the user's language, tap opens the app (see D-R4).
- Android channels per sound/vibrate choice, exact alarm when allowed, boot survival.

Out:
- Push (FCM) notifications and the template's demo scheduling helpers: `NotificationService.scheduleNotification` and the periodic ones are not used by this feature (their removal is a later cleanup, not part of this plan).
- Snooze, "mark as done", notification actions, groups.
- One-off events, day-before offerings (tiên thường), multiple reminders per event.

## Inspected evidence

- `Anniversary` already stores `reminderEnabled`, `remindDaysBefore` (0, 1, 3, 7 from the form; table allows 0 to 30) and `remindMinuteOfDay` (default 420). Nothing schedules them yet.
- `AnniversaryResolver` has `solarDateIn(date, lunarYear)`, `nextOccurrence(date, today)` and `nextHolding`; it returns `null` outside the engine's years (1800 to 2199). Leap-month and day-30 rules are already applied there, so the planner must not re-implement them.
- `AppSettings` has `sound` (`deviceDefault`, `softBell`, `silent`), `vibrate`, `remindFirstDay` (default off), `remindFullMoon` (default on), `remindFestivals` (default on). `LunarHoliday` / `LunarFestival` in `lib/services/lunar/lunar_holidays.dart` give the system-event dates.
- `NotificationAccessService` (port over `permission_handler`) reports allowed / denied / blocked.
- `NotificationService` (template singleton) already initializes `flutter_local_notifications` ^22, has one channel (`fox_channel`, "Fox Push Notification Channel", importance max) and an Android icon named `notification`. Its tap callback ignores payloads except through `onSelectNotification`; it has demo `zonedSchedule` code using `exactAllowWhileIdle`.
- `pubspec.yaml` has `flutter_local_notifications` and `timezone`, but no package that reads the device time zone, and no `clock`.
- `AndroidManifest.xml` already declares `POST_NOTIFICATIONS`, `VIBRATE`, `RECEIVE_BOOT_COMPLETED`, `SCHEDULE_EXACT_ALARM` and the plugin's scheduled and boot receivers. `USE_EXACT_ALARM` is deliberately absent. `Info.plist` has no notification code of its own (the plugin uses `UNUserNotificationCenter`).
- `docs/PRODUCT_BRIEF.md` still says "exact anniversary day, no day-before reminder"; plan 0005 D9 replaced that. The brief and `docs/GLOSSARY.md` need a one-line update in slice N5.
- Not established by inspection: whether a soft-bell sound resource exists in `android/app/src/main/res/raw` and iOS, how the Pixel 5 behaves with exact alarms on Fox's Android version, and whether a time zone package supports Swift Package Manager (checked in N2 before adding it).

## Acceptance criteria

Planner (pure Dart, no plugin):
- RS-1: For an enabled anniversary, the planner returns the fire time `occurrence − remindDaysBefore` days at `remindMinuteOfDay` in the device zone, for each occurrence inside the window. Solar dates come from `AnniversaryResolver`, checked against the oracle fixtures.
- RS-2: Disabled anniversaries, deleted ones and dates the engine cannot resolve produce no reminder, and do not stop the others.
- RS-3: Fire times at or before "now" are skipped (D-R8); an occurrence whose reminder time passed today still yields next year's.
- RS-4: Day 30 in a 29-day month and leap-month rules give the same solar date the list shows for that year (reuses the resolver, no copy of the rules).
- RS-5: The plan is sorted by fire time, capped (D-R2), and deterministic: the same input gives the same plan and the same ids.
- RS-6: System events appear only for the switches that are on (mùng 1 default off, rằm and festivals default on); they fire at a fixed default time (07:00) on the day.

Gateway and sync:
- RS-7: `syncReminders()` leaves the pending set equal to the plan; running it twice in a row leaves it unchanged.
- RS-8: With notifications not allowed, sync schedules nothing and does not ask for the permission; granting it later re-plans.
- RS-9: Creating, editing, deleting or toggling an anniversary, and changing sound, vibrate, language or a system-event switch, re-plans without opening Settings or restarting.
- RS-10: A failure scheduling one reminder is logged and does not block the rest (every catch logs or rethrows).
- RS-11: Android uses the exact mode only when the exact-alarm permission is held, otherwise the inexact mode (D-R5).

On a real device (Pixel 5, dev flavor, and iOS):
- RS-12: A reminder set a few minutes ahead fires with the app swiped away, with the right title, body and channel sound.
- RS-13: Pending reminders still exist after a device restart (Android) and after the app is force-stopped and reopened.
- RS-14: Changing the device time zone, then reopening the app, moves the reminders to the same local wall-clock time (D-R3).

- Pure rules (RS-1 to RS-6): unit tests on the planner with a fixed `now`. Expected solar dates come from `packages/lunar_calendar/test/fixtures/` (independent oracle), never from the planner or engine under test. Tests that a plausible defect is caught: mutate the days-before subtraction and the "skip past" comparison and confirm a test fails.
- Sync and gateway (RS-7 to RS-11): a hand-written fake gateway records calls; tests assert the final pending set, idempotence, the permission gate and the error path.
- Device (RS-12 to RS-14): the app's real interface. On the dev flavor, add an anniversary on today's lunar date with the reminder time two minutes ahead and 0 days before, swipe the app away, wait. Inspect side effects with `adb shell dumpsys alarm | grep ever_moon` and `adb shell dumpsys notification --noredact | grep -A3 ever_moon` before and after, then restart the phone and repeat the pending check. Clean up by deleting the test events. iOS: same on a device or simulator, checking the Notification Center. Anything not run is reported as not run.
- Existing procedures: commands in `docs/agent-engineering.md` and plan 0005's Verification block.

## Risks and checks

| Risk | Assumption that keeps it safe | Check that could disprove it |
|------|-------------------------------|------------------------------|
| iOS drops notifications beyond 64 pending | The cap of 60 plus re-plan on every start keeps the nearest ones | Unit test with 100 events asserts 60 and nearest-first; iOS device check of the pending count |
| Android kills or delays alarms on some phones (battery savers) | Exact alarm plus `allowWhileIdle` is enough on Pixel; other makers vary | RS-12 and RS-13 on the Pixel 5; the limitation on other makers is stated in the docs, not proven |
| Exact-alarm permission revoked or not granted | The inexact fallback still delivers within minutes | Unit test on the mode choice; device check with the permission off |
| Time zone package fails on SPM or Android | Choose after checking, or fall back to the fixed zone with Fox's approval | Check in N2 before adding it; `fvm flutter build` on both platforms |
| Resync cancels everything, so a crash between cancel and schedule loses reminders | Schedule first into new ids then cancel old ones if the cost is small; otherwise rely on the next start re-planning | Test that a failing schedule call leaves the old set in place (decided in N2) |
| Lunar year beyond 2199 or a resolver `null` | The planner skips and logs, others continue | RS-2 test |
| A language or sound change leaves old text or channel | Those settings are triggers for re-plan | RS-9 test |
