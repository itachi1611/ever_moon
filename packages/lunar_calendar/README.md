# lunar_calendar

Pure-Dart engine for the Vietnamese lunar calendar (time zone UTC+7), lunar years 1800 to 2199. Part of Evermoon; not published. Decisions: [ADR 0002](../../docs/adr/0002-lunar-engine-and-time-zone.md). Plan and acceptance criteria: [plan 0001](../../docs/plans/0001-lunar-package.md).

The app must not import this package directly from features; it goes through its own `LunarCalendarService` interface.

## API

```dart
import 'package:lunar_calendar/lunar_calendar.dart';

final calendar = VietnameseLunarCalendar.shared;

calendar.toLunar(DateTime(2026, 11, 6));          // LunarDate? (year, month, day, isLeapMonth)
calendar.toSolar(const LunarDate(2026, 10, 15));  // DateTime? as UTC midnight
calendar.leapMonthOf(2025);                       // int? leap month number, null if none
calendar.monthsOf(2025);                          // List<LunarMonth> in order, leap month included
```

| Rule | Behaviour |
|---|---|
| Range | Lunar years `minLunarYear` (1800) to `maxLunarYear` (2199). Outside it: `null` or an empty list. |
| Non-existent date | `toSolar` returns `null` for month 13, day 0 or 31, a leap month the year does not have, or day 30 of a 29-day month. |
| No fallback | The engine never moves day 30 to 29 or a leap month to the regular month. That is the app's anniversary rule (ADR 0001). |
| Input time | `toLunar` reads only the year, month and day fields of the `DateTime`; its time and zone are ignored. |
| Cost | Months are computed on first use and cached per instance. Share one instance (`VietnameseLunarCalendar.shared`). |

## How it works

`lib/src/astronomy/` computes events; `lib/src/calendar/` applies the rules.

- New moon: Meeus, "Astronomical Algorithms", chapter 49, with the planetary corrections.
- Sun longitude and principal terms: truncated VSOP87 (Meeus Table 32.A), FK5 correction, low-accuracy aberration and nutation.
- Delta T: Espenak and Meeus polynomials.
- Rules (from the author's published description): a month starts on the UTC+7 civil day of a new moon; month 11 contains the December solstice; when 13 months lie between two months 11, the first month after month 11 without a principal term is the leap month.

No code is copied or translated from the original JavaScript of the rules' author.

## Tests

```bash
fvm dart pub get
fvm dart analyze
fvm dart test
```

| File | Checks |
|---|---|
| `astronomy_test.dart` | New moons within 60 s of the oracle (mean about -35 s), principal terms within 90 s, the author's new moons within 5 s and on his Hanoi date |
| `months_test.dart` | LC-1: all 4948 months match the oracle, except the 13 pinned in `convention_differences.json` (author's convention, decision D7). LC-3: leap months |
| `calendar_test.dart` | LC-2: Tết 1985, 2007, 2030, 2053 and the 1984 and 1985 tables. Round trip on the first and last day of every month. LC-4: out-of-range and non-existent input |
| `fixtures_smoke_test.dart` | Fixture files load and cover 1800 to 2199 in UTC+7 |

Expected values come only from `test/fixtures/`, never from memory or from this code.

Mutation check: setting `vietnamTimeZoneHours` to 8 in `lib/src/astronomy/julian_day.dart` must turn tests red (Tết 1985 becomes the Chinese date). Set it back to 7 afterwards.

## Fixtures

`test/fixtures/` is generated by `tools/lunar_oracle/` (Python, independent `astronomy-engine` oracle), except `anchors.json`, which is transcribed by hand from the author's published tables. To regenerate, see [tools/lunar_oracle/README.md](../../tools/lunar_oracle/README.md); regeneration must reproduce the committed files byte for byte.
